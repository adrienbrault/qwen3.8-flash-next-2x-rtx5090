# The served image, layer by layer

The served configuration on `:8022` runs `tabbyapi:stack-r3-rows32` (since 2026-09-25 01:05 CEST, [R717c](../bench/results/r717-rows32.md)), the last row of the table below. Up to `-moecoopv2` the tag is the build history: each suffix is one layer built on the previous one, except `-hcmix2`, which is built on an intermediate `…-coopwide-hcmix1` (mixer round 1). From there each layer has its own Dockerfile with `ARG BASE=<previous image>`: an overlay directory's `Dockerfile.box`, or, for the four patches that sit in this directory (`verifybatch-r1.patch`, `mtpnorm-r1.patch`, `mixstate-r1.patch`, `prefbatch-r1.patch`), a `Dockerfile.tabbyapi-<name>` next to them. The `hcfast-r1` and `moefast-r1` layers are built in the order given in [`overlays/stack-r2/README.md`](overlays/stack-r2/README.md); `stack-r3` is one patch series on top, built as [`overlays/stack-r3/README.md`](overlays/stack-r3/README.md) gives, and `stack-r3-rows32` one patch on that, built as [`overlays/rows32-r4/README.md`](overlays/rows32-r4/README.md) gives. Provenance and licences for every input are in [`../THIRD_PARTY.md`](../THIRD_PARTY.md); the measurement that admitted each layer is linked in the last column and indexed in [`../bench/RESULTS.md`](../bench/RESULTS.md).

## Building the chain in one command

[`build-chain.sh`](build-chain.sh) runs the rebuild order above, 35 `docker build` calls from `qsa-cid` to `stack-r3-rows32`, each tagged the way the next layer's `BASE` and the launcher expect, and fails unless the last tag equals `DAILY_IMG` in [`../scripts/launch-flashnext.sh`](../scripts/launch-flashnext.sh). Before each build it checks that every `COPY` source exists in the build context and is not excluded by the context's `.dockerignore`. It needs x86_64 Linux and Docker with BuildKit on the `docker` driver (`docker buildx use default`), because every layer after the first is `FROM` a local tag. No GPU is used.

```sh
bash docker/build-chain.sh                                          # the served tags, tabbyapi:*
DRY_RUN=1 bash docker/build-chain.sh                                # print the 35 commands and check the COPY sources; no docker needed
IMAGE_REPO=tabbyapi-verify NO_CACHE=1 bash docker/build-chain.sh    # a verification build beside the served tags
```

`DRY_RUN=1` prints the commands and runs no docker command. `NO_CACHE=1` passes `--no-cache` to every layer. `IMAGE_REPO=<name>` builds every tag under another repository name, so a verification build cannot replace a served tag; the final check then compares the part after the colon. An existing tag is skipped, so a failed run resumes where it stopped; `FORCE=1` rebuilds it. `MAX_JOBS` sets the compile parallelism of the native layers, `LOG_DIR` the directory of the per-layer logs (default `build-logs/`). The step list was cross-checked against `docker/build-chain-podman.sh` in the `chaossrv` branch of [zorrobyte/qwen3.8-flash-next-2x-rtx5090](https://github.com/zorrobyte/qwen3.8-flash-next-2x-rtx5090), the rootless podman rebuild that found the three breaks below ([issue #1](https://github.com/adrienbrault/qwen3.8-flash-next-2x-rtx5090/issues/1)); its staged build context for `moe-coop-v2-overlay` is the reason that overlay's `Dockerfile` now copies `moe-coop-v2-overlay/test_moe_coop_v2.py`, a path that exists in the documented context.

The three breaks. The `-hcmix2` step applied `hc-mix-v2-r2.patch` to `…-coopwide`, but that patch is written against round 1 of the mixer, which the repository did not contain; `hc-mix-v2.patch` is round 1, and the chain applies it first, in its own layer, because a `patch --dry-run` cannot chain two diffs to one file. The `-mtpfix2` overlay installed the pipeline's MTP eligibility fix but not the R441 free-VRAM guard fix that the served `-mtpfix2` image also carried, so the chain produced `prefill_pipeline.py` `1a5af53b…` where the served image has `7f6e4b34…`, the baseline `ngram-prefetch-r1` pins; `memfix.py` is that fix. `Dockerfile.tabbyapi-mixstate` rebuilt the extension in `/tmp/build`, where `-qsa-cid` and the `-bszn` layers leave their objects; the layers in between install engine sources with `cp -a` or `COPY`, which keep the build context's mtimes, and from a git checkout those are older than the objects, so ninja reused a `blocksparse_mlp.o` from before `decode-kernels-r2` and the extension failed to import (`undefined symbol: exl3_moe_coop_run(…)`). `Dockerfile.tabbyapi-mixstate` and `Dockerfile.tabbyapi-bszn` now remove `/tmp/build` before the rebuild and import the rebuilt extension. The other native layers build in a new `mktemp -d` directory or in a `TORCH_EXTENSIONS_DIR` their Dockerfiles clear.
