Every layer above was admitted with byte-identical greedy output on the c1 256-token and 30k prompts (the fingerprints are in each result file), except where the layer only changes rows ≥ 9 (bszn16, coopwide at ≥ 128 slots), where the gate was GSM8K and tool-eval under concurrency instead, and E3, which changes the 30k fingerprint through the prefill accumulation order and was gated on GSM8K, needles and tool-eval.

Rebuild order: `Dockerfile.tabbyapi` → `-qsa-cid` → `-pr337` → `-bszn` ×3 (bszn16, coopwide, hc-mix-v2-r2) → `-pyfile` (hostgap) → `-pypatch` (ppipe) → the three overlays in order, then `decode-kernels-r2` → `refbase` → `decode-kernels-r4` → `stack-r4-e3r2` → `mtp-pruned-r1` → `tool-choice-r1` → `ple-ckpt-clone-r1` → `nvme-tier-r4` → `e3-det-r1` → `decode-kernels-r6` → `qsa-rawk-ring-r1` → `gdn-state-bf16-r1` → `ngram-prefetch-r1` (`docker build --build-arg BASE=<previous tag> -f overlays/<name>/Dockerfile overlays/<name>` for the first two; the MoE overlay's build context is the overlay's parent and it takes `--build-arg BASE=<tag>`, not an image id; `decode-kernels-r6` keeps its Dockerfile in `overlay/`: `docker build --build-arg BASE=<tag> -f overlays/decode-kernels-r6/overlay/Dockerfile.box overlays/decode-kernels-r6`; `qsa-rawk-ring-r1` keeps it at the overlay root: `docker build --build-arg BASE=<tag> -f overlays/qsa-rawk-ring-r1/Dockerfile.box overlays/qsa-rawk-ring-r1`, and `gdn-state-bf16-r1` the same way with `--build-arg MANIFEST=manifest-on-r6.json`). The Dockerfiles pin TabbyAPI by SHA and ExLlamaV3 by version and assert both at build time.
