## Mapping r1 onto the served tree

Since r1, the installed generator includes stack-r2/r3 device MTP and pruned embedding, batch verify and pinned staging, grouped MTP acceptance prefill, rows32 staging, recurrent checkpoint/tail capture, merged prefill, and R825's resumable whole-prompt pipeline. ## Proposal and logits paths

`EXL3_PROMPT_LOOKUP=0` is the image and source default. Only `0` and `1` are accepted. ON requires fixed-depth MTP; dynamic confidence drafting is rejected. OFF keeps the served drafter's tensor operations, target forward, samplers and rollback. Additive CPU metrics/log fields are the only OFF differences.

ON waits for at least three generated tokens before allocating/indexing its CPU SAM. The index sees committed sequence IDs, never unverified page-buffer writes. It chooses the existing SAM's earliest source for the longest previous suffix of at least three tokens. Source/suffix bounds, suffix equality, remaining output budget and exact multimodal spans must all pass; a complete current draft window must be available. EOS and stop IDs are not prefiltered: the real sampler and `receive_sample` decide them.

The MTP head always supplies column zero, using the same served device/pruned path and depth-zero head. Lookup can replace only columns 1 through depth-1 if that opener equals the continuation's first ID. A round with no valid source does not read the opener back early. A source with a mismatching opener keeps MTP. Every row still returns the policy's full width, never a new verify shape.

When every row has a hit, write the complete chains directly to the host draft buffer and skip the remaining MTP forwards. The opener readback has completed; uploading a CPU lookup chain just to read it back would add an unnecessary sync. In a mixed batch, run every original MTP forward at the original batch size and then overwrite only hit-row tail columns. This intentionally gives up r1's compact-miss optimization: it retains current head/device/scratch geometry and is inexpensive to reason about. c1 receives the full skip benefit. At c2/c3 only all-hit rounds save draft forwards; the gate measures their net effect.

R501 FINDINGS records OFF/OFF-b divergence at code token 250 and prose token 142, and an OFF/ON code flip at token zero. Its explanation was a changed last-prefill forward shape exposing a near tie in an unstable in-process harness; the four served arms remained canonical. The unique numerical root cause was not proven. A lookup proposal cannot explain token zero with the generated-token guard. R827 eliminates the selector-dependent prefill/logits-path hypothesis in its source: no prefill edit, no sampler edit, no device-mode switch, no compact miss batch, and no SAM before token three. CPU AST checks compare the actual target forward and receive_logits/receive_sample code to the served base, and execute base/OFF/ON MTP loops on host/device tensor doubles. Served GPU byte identity, including OFF/OFF stability, is still mandatory; static evidence is not a GPU proof.

## R825, checkpoints, rows and rollback

R825's resumable window is the layer-split **prefill** runtime. It is separate from the optional MTP KV ring. `Generator.iterate` resumes it before admitting new decode work; lookup runs only for `is_prefill_done()` jobs. `prefill_pipeline`, merged snapshot/capture publication, pipeline streams and commit boundaries are untouched. No partial resumable window can enter the lookup index.

R823p's 4096-token PP interval, 12288-token tail span, in-forward captures and near-end/page-boundary handling remain the supplied daily's. At a recurrent checkpoint boundary, target verification rejects the unresolved suffix through the served `reject_remainder`, even when a proposal matches. Lookup does not cross a checkpoint by bypassing its acceptance rule.

The launcher policy remains `[[4, 3], [8, 2]]`: depth 3 for c1-c4 (4, 8, 12, 16 flattened verify rows), depth 2 for c5-c8 (15, 18, 21, 24 rows). Lookup occupies existing columns: two copied tokens at depth 3, one at depth 2, inert at depth 1. The opener is MTP and is never credited as a copied lookup token. rows32 dense, MoE and shared-expert selectors retain their 32-row capacity; legacy 16-row branches are not enlarged. At c1-c3 the flattened window stays under 16; at c4 it equals 16, and c6-c8 rely on the existing rows32 kernels. No cache page, max_q_size, recurrent history depth or scratch capacity grows. The optional MTP KV window is absent from the supplied live environment.

On rejection, the target's recurrent history rewinds by unresolved columns. Each affected page's write frontier is decremented across page boundaries; `seq.kv_position` remains the committed position advanced by receive_sample. Rejected K/V cells are dead until overwritten. The actual nested rollback helper is CPU-tested across page boundaries, including zero rejected columns. EOS and requeue stop accepting immediately. Banned-string rewind retains the served rollback/state replacement and additionally resets the CPU SAM, so same-length replacement cannot leave a stale match. The round mask is discarded afterwards.

The existing MTP acceptance repair prefills accepted IDs with their target hidden states. It repairs the columns whose speculative MTP forwards were skipped. The served non-windowed cache keeps its original padded batched repair. If a windowed cache is selected elsewhere, its existing exact-width accepted-length groups remain intact, avoiding ring writes that alias live committed cells. Neither repair nor allocation/deallocation/requeue code is replaced by r1.

## Counters, clients and gate

Counters are cumulative per logical request across physical requeues: `decode_steps`, `lookup_checks`, `lookup_hits`, `lookup_proposed`, `lookup_accepted`. A step is one real target verify call for that job, including ordinary no-draft steps. Hits require a full MTP-opened chain; proposed/accepted credit counts only copied tail columns. Acceptance increments only inside the existing successful comparison branch, after target sampling/commit and stop/checkpoint checks. EOS results are updated after the round's acceptance accounting and before page release/requeue. Tabby carries all scalars through its existing stream merger. Generation seconds use the unrounded backend value in the new counter line; existing timing fields are unchanged.

The strict counter/completion join uses the real HTTP completion serial. Each cell must contain exactly its expected number of logical requests, so foreign or missing requests invalidate the run. Warmups are excluded by selecting only the final measured request serials after all warmup requests finish. Per-stream and aggregate server metrics are `1000 * gen_time / decode_steps`, generated `tokens / decode_steps`, `hits / checks`, and `lookup_accepted / decode_steps`. These are server generation time measurements, not CUDA-event kernel timings. Client per-stream decode is `(completion_tokens - 1)/(last-first SSE timestamp)`. SSE frames are not treated as token counts. Malformed JSON, absent usage/finish, errors, missing keys, inconsistent accounting or missing DONE fail closed. A one-frame short answer is valid identity evidence; it cannot supply a speed measurement and is rejected only by the speed validator.

Identity uses the existing fn five-short plus deterministic 100k prompt (6/6), chat five prompts plus the long B-tree/requeue request (6/6), and twelve fixed real-file edit prompts (12/12). Raw channel text, reasoning, function arguments, finish and token count must match all four boots; tool-call IDs are not output content. The code context repeats three revisions of each of six archived real probe files, following R501's file-rewrite workload with two small edits per file. Agent identities force 3072 tokens and disable thinking; speed forces 2048 tokens to fit the GPU budget. Both ON identity boots must show hits and accepted copied tokens. The long chat request forces 5000 tokens to cross requeue boundaries.

Speed runs the unchanged archived R813 fn_bench through `fn_driver.py`, which audits each original SSE line and rejects its historically skipped malformed JSON or missing DONE/finish/usage. Requests and timing formulas remain unchanged. The loop uses `--distinct`, c1/c2/c3 code and prose, 1024 tokens, one full warmup and three measured rounds. Agent c1 runs one 12-request warmup and three 12-request measured passes. ON1 pairs with OFF1, ON2 with OFF2 for the -1% fn shape floor. For agent c1 every ON boot must exceed every OFF boot by at least 2%, using each boot's median per-stream decode rate. A single failed condition cannot be hidden by pooling boots. Gate replay tests eligibility, one slow ON boot, one fast OFF boot, a bad fn shape, missing rows, inactive lookup and an OFF/OFF token-zero flip.

Dry-run uses the current daily for ~180 seconds after drain, with no restart. It exercises the actual fn/chat/edit request paths, speed warmup/measured loops, usage/accounting, runtime/env/config, real wrapped completion logs and clocks. The unpatched parent cannot emit R827 counters: its old log parser is tested on actual responses and the new counter/gate branches are separately replayed on explicitly synthetic fixtures. Real SSE events and R813 records are archived with provenance. Dry PASS is bound to packet/unit hashes, LIVE md5 and 24-hour freshness. It cannot certify future candidate boot identity or new GPU kernels.

Both stages register with gpu-queue before flock and drain Olla while measuring on :8022. GPU stage snapshots the LIVE launcher, then boots OFF1/ON1/ON2/OFF2 once each using the same full candidate image ID, with only the lookup selector different. Per-boot image/env/config/landing/warm-up/residency and post-cell clocks are asserted. Any signal or error invokes bounded cleanup; the last queued unit restores through LIVE with a clean environment and no selector/image overrides. A queued successor gets the GPUs without an intermediate daily reboot. Candidate path/md5 and DECISION are printed; LIVE is never edited.
